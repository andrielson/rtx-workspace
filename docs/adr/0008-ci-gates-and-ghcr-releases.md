# CI pull-request gates and semver GHCR releases

The repository is public and its product is an image, so CI both gates changes and publishes them: `.github/workflows/ci.yml` runs the hygiene battery (the `pre-commit` gates — Biome, Prettier, `tsc`, ShellCheck, Compose validation) on every pull-request event, drafts included, and the full Bun suite once the PR is ready for review (`ready_for_review` re-triggers the workflow; the suite's own global hooks build the image through the Tests stack, so CI never duplicates that build as a separate step); a merge to `main` — squash-only, with direct pushes blocked by a ruleset requiring the pull request and both checks, administrators included — re-runs hygiene and cuts a Release exactly when `version` in `package.json` moved: the release job reads the version, and if git tag `v{version}` is missing it builds `src/` with buildx (`--pull`, OCI labels carrying version, revision and source) and pushes `v{version}` plus `latest` to `ghcr.io/andrielson/rtx-workspace`, then creates the git tag and GitHub Release. The tag is the publication record, which makes the flow idempotent and self-healing: a merge without a bump publishes nothing, and a publish that fails mid-flight (network, registry) is retried whole by the next merge or a `workflow_dispatch` on `main`, because the tag never landed; the version therefore lives in exactly one place — the field was absent until the workflow's own PR added `1.0.0`, whose merge became the first Release. Date-based tags and semver-from-labels were rejected: a date tag says when, not what, and collides across same-day merges; labels derive the number at merge time from information a reviewer never saw, while the package.json bump is ordinary reviewed code.

The release build is a rebuild, not a retag: PR runs and merge runs execute on different ephemeral runners, so no image survives between them, and transferring one as a workflow artifact would upload ~1–2 GB on every PR run for a merge that may never happen. The economy comes from registry cache instead: every release exports both a `buildcache` manifest (`type=registry`) for the release job's own next run and inline cache metadata inside the pushed image; PR runs warm the daemon-side BuildKit cache with a plain `docker build --cache-from` over `latest` before `bun test`, so the Tests stack's `compose build --pull` resolves as cache hits — the Tests stack itself stays untouched (standalone per ADR 0007; its documented `cache_from: type=registry` support was the rejected alternative, coupling the stack to this registry). Residual window, accepted: `ubuntu:26.04` and `tianon/gosu` float, so a release built hours after its PR run may pick up moved bases — digest pinning is the escape hatch if it ever bites. The suite's flaky half (`user-install`, real vendor endpoints — the same flakiness that keeps the full suite out of `pre-push`, issue #18) gets exactly one full-suite retry in CI: a hiccup gets a second chance while a real regression fails deterministically twice, and the retry never narrows to the flaky block, which would let a passing retry paint over a `Dockerfile`-block failure.

Security posture, given a public repository: the workflow never uses `pull_request_target` — the classic supply-chain pattern of base-repo permissions running fork code; PR runs use plain `pull_request` with the fork's read-only token and no secrets, the publish path is `push` to `main` (which a fork cannot produce and the ruleset gates anyway), and the release job additionally guards on `github.repository == 'andrielson/rtx-workspace'`. Third-party actions are pinned by commit SHA rather than moving tags (the `tj-actions` incident's vector), permissions default to `contents: read` and rise to `contents: write` plus `packages: write` only on the release job, and a `workflow_dispatch` on `main` may publish without waiting for the suite — it is a deliberate manual act by the repository owner. GitHub creates the GHCR package private on first push; it is flipped to public once, manually — the repository itself is public and its history audited clean (2026-09-13), and the image bakes no secrets (the suite's throwaway SSH keypair is generated at runtime).
